# Record permutation pilot results

Five of eight declared workloads cleared the diagnostic threshold of 1.3× on both seeds. The highest pair was 1.367× and 1.399× for 1,048,576 uniform keys in 128-byte records. These ratios substitute the measured sequential-copy time for the gather phase. They estimate headroom for a candidate and include no candidate execution.

Materialization accounted for 50.6–68.2% of the indirect references' median end-to-end time by seed. For the larger uniform 128-byte case, the estimate crossed the threshold on only one seed (1.316× and 1.295×). The larger 128-byte low-cardinality case behaved similarly, and the larger 64-byte low-cardinality case fell short on both seeds. The results support prototyping across the declared matrix, with limited margin for the cost of building a permutation schedule.

All 192 measured outputs and 64 warm-ups passed complete verification on an AMD Ryzen 7 5800X, Windows 11, GCC 16.1.0, one thread pinned to logical CPU 4. Peak process working set was 1,179,590,656 bytes (1,125 MiB), including the benchmark and verification workspace. At the largest size, each 128-byte input and output array used 512 MiB. An indirect method additionally allocated 32 MiB for packed keys and indices. The shared eviction buffer was 64 MiB and the verifier used 4 MiB for source IDs after the packed index had been released.

The pilot covers one machine, synthetic keys and a fixed out-of-place contract. Three repetitions per seed provide a screen. Cache misses, TLB misses and DRAM counters were not measured. Competitive comparisons against IPS⁴o and a record-oriented SIMD sort remain open. The sequential copy has different access patterns and allocation timing, so it is an empirical proxy for headroom.
