# Page reuse with real overlapping flight departures

Registered 2026-11-16 before extracting departure values or computing merge geometry.

## Input and batch rules

- Use the complete [OpenIntro New York City flight sample](https://openintrostat.github.io/openintro/reference/nycflights.html), published Git revision `b37b235dd702363d5ad87af68dff9533cc148160`, `data/nycflights.rda` blob `7ae458bb4baa4b32523ac495f6e96431413cb323`. It is a random sample of NYC departures from 2013. Retain every row with an integral departure delay, valid departure clock, valid published date and valid origin. A clock value of 2400 is midnight. Keep repeated keys and report exclusions.
- Use the published date and local time labels, without timezone adjustment. The scheduled minute within the day is `(actual_clock_minute - departure_delay) % 1440`. Add it to the published date, and add the signed delay to obtain the actual departure time on the replay clock, including midnight crossings. Cross-check the schedule against the supplied hour and minute fields and report the agreement. Rows remain distinct by their position in the file.
- Use two preregistered regimes. For **adjacent batches**, use the 8th, 15th and 22nd of every month of 2013 at 12:00 local time. At each cut, take the seven days immediately before and the seven days immediately after according to actual departure. Use one day per side as a control. For **parallel feeds**, use actual departures from the same calendar month separately for each of the three airport pairs (EWR and JFK, EWR and LGA, JFK and LGA). A monthly pair models combining reports from two sources and covers the same date interval for both airports. Run all 108 cases. These are reproducible replay boundaries. The source does not give arrival times at an ingestion service.
- Within each batch, sort by scheduled minute and then original row number. At a tie between batches, take the left batch first. In the adjacent replay, it is the earlier batch. For airport pairs, it is the first airport by lexicographic code. No record is repeated within a pair.

## Model, comparisons and decision

- The model uses synthetic 128-byte records, 4 KiB pages and a 64 KiB minimum mapping extent, matching the earlier merge. Use the existing fixed, page-aligned input/output geometry as the reference. Compare the best one-time output offset with the inputs already aligned, and a planning ceiling with page-aligned output and separate input offsets chosen before payloads are written. All offsets range from zero through 31 rows. For every case, also count the bytes in any single-source slices long enough to contain a 64 KiB extent before alignment constraints. This upper bound ignores page-end fragments.
- Report the number and proportion of rows within the closed intersection of the two scheduled-time ranges when they share an interval of positive duration, the number of same-source slices, longest slice, and exact eligible bytes for each contract. Cross-check the rank-based slice calculation against an independent record-level sorted merge and an explicit page table model, including every offset. Summaries compare only geometrical eligibility. There is no timing of a merge.
- Multiple cases share rows. A regime clears the screen for a timing follow-up only if at least two of its main cases have at least 5% of rows inside the shared scheduled-time interval and at least 37.5% reusable bytes with the 64 KiB cutoff. The latter is the smallest reusable fraction observed to clear the 1.30× threshold in the earlier synthetic fresh-output merge. The one-day controls cannot rescue the gate. A post-hoc choice of output/input offset is part of the declared candidate calculation. No other input filtering or selection based on the outcome is allowed.
- If any proposed alignment passes, inspect the size and concentration of the successful cases before scheduling timing on an independent, denser source. The independent-input choice assumes newly generated buffers and excludes planning and construction costs. A reported gain in reusable bytes is a ceiling, with no implication that a caller can use it on already resident runs or that a complete pipeline gets a speedup.
